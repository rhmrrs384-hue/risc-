As programs get larger, "spaghetti code" becomes a problem. Functions let you break programs into smaller modules with clear responsibilities. Each module can be developed, debugged and reused independently.

Shows a basic example:

The problem: When foo calls bar, we don't know if bar overwrites t0. So when we return, t0 may no longer hold what we saved.
Key points:

call is a pseudo-instruction that jumps to the function AND saves the return address in ra
ret jumps back to where the function was called from (reads ra)
Never assume what registers a called function uses — you must save what you need


Image 2 - The Stack Solution
The Diagram shows:
When f calls f again (recursion), the second call would overwrite the saved values. So we need the stack.
What is a Stack?

A region of memory that works Last In First Out (LIFO)
Each function allocates a stack frame — its own private space
Stack grows downwards in memory
sp (stack pointer) always points to the last used byte

Stack Frame Example:
asmfoo:
    addi sp, sp, -8   # allocate frame (make space)
    sw   t0, 0(sp)    # save t0
    sw   ra, 4(sp)    # save return address
    call bar
    lw   ra, 4(sp)    # restore ra
    lw   t0, 0(sp)    # restore t0
    addi sp, sp, 8    # deallocate frame
    ret

Image 3 - Stack Frame Layout
A stack frame typically contains:
SectionContentsTopExtra arguments (9th, 10th...)Saved registersLocal variablesBottom ↓Stack grows downward
Key Concepts:

First 8 arguments go in registers a0–a7
Extra arguments go on the stack
Callee-save registers — the called function must preserve these (save & restore)
Caller-save registers — the caller must save these if it needs them after the call
Frame pointer (fp/s0) — optionally points to a fixed point in the frame, useful when frame size isn't known at compile time
The prologue (start of function) builds the frame, the epilogue (end) tears it down

t registers — Temporaries (t0–t6)
Use for: scratch work, loop counters, intermediate calculations — anything short-lived.

If you call another function, assume t registers get destroyed
Use freely inside a single subroutine


a registers — Arguments & Return values (a0–a7)
Use for: passing arguments INTO a function, and returning values OUT.
asm# Caller sets up arguments:

Good question! Let's think through this carefully.

The check digit value (result of validation function)
The result is a remainder from modulo 97, so it's a value between 0 and 96 — that fits in a byte, but it's a number, not an ASCII character yet.

What you need to do
You need to compute 98 - result, which gives you a number (1–98), then convert it to a 2-digit ASCII string to store in the IBAN buffer.

So: lhu or sh?
Neither is the right tool for this step. Here's why:

lhu = load halfword unsigned (reading 2 bytes from memory) — you'd use this if you were reading the check digits back
sh = store halfword (writing 2 bytes) — tempting, but the two digits are two separate ASCII characters at two separate byte addresses
What you actually want:
asm

# Extract tens digit
li   t1, 10
div  t2, t0, t1        # t2 = tens digit (0-9)
rem  t3, t0, t1        # t3 = units digit (0-9)

# Convert to ASCII
addi t2, t2, '0'       # '0' = 48
addi t3, t3, '0'

# Store into IBAN buffer at positions [2] and [3]
sb   t2, 2(a0)         # IBAN[2] = tens digit
sb   t3, 3(a0)         # IBAN[3] = units digit
Why sb (store byte) twice, not sh?
Because the IBAN buffer holds individual ASCII characters — "DE" at [0-1], check digits at [2-3], BLZ at [4-11], KNR at [12-21]. Each character is 1 byte. Using sh would work on little-endian only and would be confusing/fragile. Two sb instructions is the clean, correct approach.

a0 is still the IBAN base here ✓ — but the IBAN currently has '1','1' (ASCII 49) at positions [2][3] as placeholder.

The spec says: set check digits to '0' (48), not '1' (49) before calling validate!

Look at your earlier code:

riscv
li     t3 49      # ← THIS IS '1', should be 48 = '0'
Fix — just change 49 to 48:
riscv
li     t3, 48     # '0' placeholder, not '1'
addi   t0, t0, 1
sb     t3, 0(t0)
addi   t0, t0, 1
sb     t3, 0(t0)
The IBAN must read DE00... when passed to validate_checksum, then you replace [2][3] with the real check digits. That one byte difference is why you get 76 instead of 87.
